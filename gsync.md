# gsync

Безопасно стянуть свежее из удалённого репозитория. Одной командой — хоть
по одному репозиторию, хоть по всем сразу.

Личный инструмент, не часть какого-либо проекта. Живёт в
`~/.local/bin/gsync`, работает с любым git-репозиторием.

---

## Зачем он есть

Короткий ответ: `git pull` делает РАЗНОЕ в зависимости от того, в каком
состоянии репозиторий, а состояние в момент запуска обычно неизвестно.

Длинный — история, из-за которой скрипт и появился. Работа шла на двух
машинах. На одной коммит уехал на GitHub, потом у него правилось
сообщение через `git commit --amend` — а это создаёт НОВЫЙ коммит взамен
отправленного. Ветки разошлись: один коммит свой, один чужой. Обычный
`git push` отказал, `git pull` в такой ситуации по умолчанию сделал бы
merge-коммит на ровном месте, и разбираться пришлось бы задним числом.

Вывод оттуда: перед тем как что-то тянуть, надо СНАЧАЛА посмотреть, что
происходит, и только потом действовать. Именно это gsync и делает.

## Что он делает и чего не делает

Единственное изменяющее действие — **перемотка вперёд**
(`git merge --ff-only`), и только когда своих коммитов нет вовсе, а в
рабочем каталоге чисто. Это сдвиг указателя ветки на то, что уже лежит
на удалённом: потерять при нём нечего.

Во всех остальных случаях скрипт **называет состояние словами, печатает
готовую команду и НИЧЕГО НЕ ДЕЛАЕТ**. Решение за человеком.

Не делает НИКОГДА, ни при каких ключах:

* не коммитит и не откатывает правки;
* не прячет в `stash` — забытый stash находится через месяцы;
* не сливает ветки (кроме перемотки) и не переписывает историю;
* ничего не отправляет на удалённый репозиторий;
* не трогает репозиторий, в котором нужен выбор человека.

Почему разошедшиеся ветки он не чинит сам, хотя лечатся они одной
командой `git pull --rebase`: rebase может встать на конфликте, и
получить конфликт внезапно, посреди обхода пяти репозиториев, — худшее,
что может случиться с тем, кто git знает неглубоко.

## Как пользоваться

```zsh
gsync                          # текущий каталог
gsync <PATH>    # ВСЕ репозитории внутри каталога
gsync -n <PATH>  # только посмотреть, ничего не менять
gsync --install                # поставить/обновить себя в ~/.local/bin
gsync --help
```

Второй вариант — основной сценарий: сел за другую машину, одной командой
обошёл всё, увидел, где что.

Каталог просматривается **на один уровень вглубь**. Рекурсия по всему
дереву нашла бы чужие репозитории внутри `node_modules` и подобного.

Код возврата: `0` — всё в порядке либо перемотано; `1` — хоть один
репозиторий требует внимания; `2` — неизвестный ключ.

## Что он скажет и что это значит

| Состояние репозитория | Что делает gsync | Что делать вам |
|---|---|---|
| совпадает с удалённым | говорит «стягивать нечего» | ничего |
| отстаёт | **перематывает вперёд**, показывает приехавшие коммиты | ничего |
| есть свои неотправленные коммиты | не трогает | `git push` |
| ветки разошлись | не трогает | `git pull --rebase`, при конфликте — `git rebase --abort` |
| незакоммиченные правки | перечисляет их, не трогает | закоммитить или `git restore <файл>`, потом снова gsync |
| `HEAD` отсоединён (не на ветке) | не трогает | `git switch main` |
| ветка не связана с удалённой | не трогает | `git config --global push.autoSetupRemote true`, затем обычный `git push` |
| удалённый недоступен | не трогает | проверить сеть; если просит пароль — GitHub его не принимает с 2021 года, нужен Personal Access Token |

## Установка на новой машине

Скрипт ставит себя сам. Скачать `gsync` (и `gsync.md` рядом, если нужен)
в любой каталог и выполнить:

```zsh
bash ~/Downloads/gsync --install
```

Он скопирует себя в `~/.local/bin/gsync`, выставит права `755`, заберёт
туда же лежащее рядом описание и скажет, если `~/.local/bin` не в
`PATH`. Файлы настроек оболочки он **не правит сам** — печатает строку,
которую надо добавить, и в какой файл.

Повторный запуск — это обновление: перезапишет прежнюю версию и скажет
об этом.

**Руками `mv` лучше не устанавливать, и это не вкусовщина.** У `mv` есть
свойство: если назначение — существующий каталог, файл кладётся ВНУТРЬ
него, молча. Ровно так 2026-09-15 получился `~/.local/bin/gsync/gsync`,
поиск по `PATH` упёрся в каталог, оболочка сказала «permission denied»,
и по этому сообщению причину не угадать. `--install` этот случай
разбирает явно.

Нужен `bash` (не `sh`: в скрипте массивы) и `git`. Больше ничего.

## Если что-то не запускается

**`zsh: permission denied: gsync`** — оболочка НАШЛА `gsync` в `PATH` и
не смогла выполнить. Почти всегда это значит, что `~/.local/bin/gsync`
— каталог, а не файл (см. выше про `mv`). Посмотреть и починить:

```zsh
ls -la ~/.local/bin/gsync        # если это каталог — заберите своё изнутри
rmdir ~/.local/bin/gsync         # откажется, если внутри что-то осталось
bash ~/Downloads/gsync --install
```

`rmdir`, а не `rm -rf`: он отказывается удалять непустой каталог. Здесь
это защита — внутрь могло уехать чужое.

**`zsh: command not found: gsync`** — противоположный случай: файл не
найден вовсе. Либо не установлен, либо `~/.local/bin` не в `PATH`.
Проверить: `ls -l ~/.local/bin/gsync` и `echo $PATH`.

**Ничего не печатает и сразу возвращается** — вы не в репозитории и не в
каталоге с репозиториями. Путь можно указать явно: `gsync ~/проекты`.

## Почему он в домашнем каталоге, а не в репозитории проекта

Он про РАБОТУ С репозиториями, а не про какой-то один из них. Положи его
в проект — и на второй проект его придётся копировать, после чего копии
разойдутся.

Обратная сторона: он не версионируется и на новой машине его надо
ставить руками. Если инструментов такого рода станет несколько — завести
отдельный небольшой репозиторий с настройками и класть их туда, а в
`~/.local/bin` держать ссылки.

## Что проверено при написании

Собрана песочница из семи репозиториев, по одному на каждое состояние
из таблицы выше, и на ней прогнано. Отдельно проверено главное: в
четырёх случаях, где скрипт отказался действовать, после прогона НИЧЕГО
не изменилось — коммиты на месте, правки в рабочем каталоге целы
построчно, отсоединённая голова как была.

Проверены и края: каталог без репозиториев, несуществующий путь,
недоступный удалённый, неизвестный ключ, пробел в пути, повторный
прогон, `--dry-run`.

**Не проверялось:** настоящий GitHub по HTTPS с токеном — в песочнице
удалённые репозитории локальные. Если `fetch` упрётся в
аутентификацию, скрипт это назовёт, но сам сценарий не воспроизводился.

## Если понадобится поправить

Логика состояний — одна функция `sync_one`, читается сверху вниз в том
же порядке, в каком идут строки таблицы. Каждая ветка заканчивается
`return`, так что добавить новый случай — значит вставить блок в нужное
место, а не разбираться во вложенных условиях.

Цвет включается только для терминала (`[ -t 1 ]`) и глушится переменной
`NO_COLOR`: вывод иногда кладут в файл, и escape-последовательности
уехали бы туда же.
